# Hisense AEH-W4E1 Air Conditioner for Home Assistant

A native (custom component) Home Assistant integration for air conditioners with a **Hisense AEH-W4B1 / AEH-W4E1** WiFi module (**Ayla Networks** platform, LAN mode). **Direct and local** control — no add-on, no MQTT bridge, and (after setup) no cloud.

> Built as a direct, local implementation of the **Ayla Networks LAN mode** protocol. The OEM app secret/ID tables are derived from the [AirCon](https://github.com/deiger/AirCon) add-on (GPL-3.0); see [License and credits](#license-and-credits).

---

## How it works (architecture)

The AEH-W4E1 module does not expose an API you can connect to: in LAN mode it works **in reverse**.

1. The integration starts a small **local HTTP server** and **registers** with the module by sending a `POST/PUT http://<module_ip>/local_reg.json` every ~10 s, advertising the `ip:port` where it can be reached (keep-alive; the module answers `202 Accepted`).
2. The module **connects back** to the server and establishes an encrypted channel (`/local_lan/key_exchange.json`, AES-CBC + HMAC-SHA256 derived from the `lanip_key`).
3. The module **polls commands** (`/local_lan/commands.json`) and **pushes encrypted state** (`/local_lan/property/datapoint.json`) — both in response to our commands and spontaneously (e.g. when using the remote control).

This is why the integration reports `iot_class: local_push`: state arrives from the device in real time.

### Is the cloud required?

**Only once.** The `lanip_key` (a per-device secret generated by the Ayla backend when the device is paired to the OEM app) can be obtained in two ways:

| Method | Cloud? | When to use it |
|---|---|---|
| **Cloud (discovery)** | Yes, one time | First use: sign in once with the OEM app credentials; afterwards the integration is 100% local. |
| **Manual** | No | You already have the key (e.g. from a previous setup). |

After setup you can **block the air conditioners from the internet**: operation is unaffected.

### The LAN server port

By default the integration **does not pick arbitrary ports**: the server binds to a **free system-assigned port** (`0` = ephemeral, so it can never conflict). The actual bound port is re-advertised to the module on every keep-alive, so it can change across restarts without problems. If you need stable firewall rules you can pin a port in the options; if it is taken you get a **repair issue** instead of a silent error.

## Supported devices

- **Hisense** air conditioners with an **AEH-W4B1 / AEH-W4E1** module.
- OEM brands based on the same modules: **Beko, Westinghouse, Winia, Tornado, York, Denali Aire, SunHome, HAXXAIR** and others (the OEM app used for pairing determines the app code).
- **Fujitsu FGLair** (AP-Wxxx modules).

**NOT supported**: **AEH-W4A1 / W4G1 / newer Hisense** modules — they use a completely different protocol (Ayla new-gen).

## Requirements

- Home Assistant **2024.12 or newer** (tested up to 2026.2).
- The air conditioner's module must have been **paired to the OEM app** at least once (that is where the LAN key comes from).
- A **static or DHCP-reserved IP** for the air conditioner is recommended.
- HA must be able to reach the air conditioner on **port 80/TCP**, and the air conditioner must be able to reach HA on the LAN server port (automatic or pinned in the options).

⚠️ **Different VLANs/subnets**: the module **rejects (`403`) registrations whose advertised IP is outside its own subnet**. If HA has multiple interfaces, set the IP **on the air conditioner's subnet** (`local_ip`) in the options.

## Installation (HACS)

1. HACS → ⋮ → *Custom repositories* → URL of this repository → category *Integration*.
2. Install "Hisense AEH-W4E1".
3. Restart Home Assistant.
4. *Settings → Devices & services → Add integration* → **Hisense AEH-W4E1**.

## Configuration

Two methods from the integration menu:

1. **Cloud (one-time, default)** — pick the OEM app, sign in, pick the air conditioner: the integration downloads key and IP. No cloud access after setup.
2. **Manual** — IP + `lanip_key` + `lanip_key_id`. Get the key from the cloud method.

To add more air conditioners, repeat the configuration (one entry per unit; the LAN server is shared).

### Options

| Option | Default | Notes |
|---|---|---|
| LAN server port | `0` (automatic) | `0` = free system-assigned port (recommended); or a fixed port for firewalls. |
| Advertised IP | auto | Set it in multi-VLAN scenarios (see above). |
| Full status refresh | 600 s | Polls all properties. |
| Keep-alive | 10 s | Registration frequency towards the module. |
| Network scan | 900 s | `0` disables it; detects **new modules** that are not configured and raises a repair issue. |
| Network to scan | auto | CIDR (e.g. `192.168.1.0/24`) if auto-detection is not enough. |

## Entities

### Climate
- **Modes**: off, fan-only, heat, cool, dry, auto (`t_power` + `t_work_mode`).
- **Target temperature** (`t_temp`), limits 16–30 °C / 61–86 °F, **ambient temperature** (`f_temp_in`).
- **Fan**: auto, quiet (lower), low, medium, high, max (higher) — `t_fan_speed`.
- **Vertical swing** (`t_fan_power`) and **horizontal swing** (`t_fan_leftright`) as separate controls.
- **Presets**: Eco (`t_eco`), Fast cool/heat (`t_temp_heatcold`, with automatic fan/silent/sleep/8° reset like the app), 8° heat (`t_temp_eight`), Sleep curves 1–4 (`t_sleep`).
- Models that use the aggregated `t_control_value` bitmap are handled natively (per-field encoding with presence bits, scaling for the Fahrenheit range).

### Switch
- **Display backlight** (`t_backlight`, inverted module semantics handled).
- **Silent mode** (`t_fan_mute`).
- *Disabled by default*: display power (`t_display_power`), double frequency (`t_run_mode`).

### Sensors
- **Humidity** (`f_humidity`), **ambient temperature** (`f_temp_in`).
- *Diagnostic, disabled*: voltage (`f_voltage`), electricity (`f_electricity`).

### Binary sensors
- **Filter needs cleaning** (`f_filterclean`).
- **Fault** (aggregate of all `f_e_*`, `problem` device class, attribute listing the active faults).

## Services

- `aeh_w4e1.send_command` — raw property write (with enum/temperature conversion and validation).
- `aeh_w4e1.request_status_refresh` — queues a full status poll.
- `aeh_w4e1.scan_network` — scans the subnet and fires the `aeh_w4e1_scan_completed` event.

All support targeting by entity / device / config entry.

## Network resilience (designed, not best-effort)

| Event | Behaviour |
|---|---|
| **Module IP change** (DHCP) | The new IP is learned from the connection (key exchange) and re-confirmed **cryptographically** on every datapoint: messages are attributed to the right device even if two modules swap IPs. If the module becomes unreachable, a **MAC-targeted scan** finds it and re-registers it automatically at the new address. |
| **Disconnect / power cycle** | Exponential backoff on failed registrations; entities become unavailable; automatic recovery. |
| **New module on the network** | Periodic scan → "new module found" repair issue (with IP and MAC). |
| **Port already in use** | Only when pinned manually: repair issue with instructions; the automatic port cannot conflict. |
| **Replaced key** (module re-paired to another account) | Detected by the key exchange → repair issue with the new `key_id`. |
| **Write to unconfirmed IP** | Writes are **held back** until the IP→device association has been re-confirmed by an authenticated exchange: no command can land on the wrong air conditioner. |

## Diagnostics & repairs

- *Settings → Devices & services → … → Download diagnostics*: runtime state (availability, bitmap in use, trusted binding, command queue, all properties) with IP, MAC, DSN and keys **redacted**.
- The **Repairs** panel collects: unknown module connected, port could not be bound, new modules found.

## Quality and documented technical limitations

- Quality scale: **Gold** reached where applicable to a custom integration; **Platinum**: shared aiohttp session, fully async, strict typing.
- *Native discovery (SSDP/Zeroconf)*: **not possible** — the Ayla protocol has no announcements; mitigated by network scan + import + one-time cloud.
- *Reauth*: not applicable — no credentials are stored (the cloud is used only during setup).
- The `status.json` probe is empirical (an endpoint not officially documented by Ayla): it is only used for a conservative fingerprint (`mac` + typical keys), never to write to the module.
- Tests: end-to-end protocol suite with a **simulated module** (registration, key exchange, encrypted commands, status pushes, signature validation, unknown-module rejection, scanner, bitmap, encryption) — `pytest tests/`.
